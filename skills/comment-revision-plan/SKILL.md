# 评论导出包解压与修改计划梳理

## 目的

输入平台导出的评论压缩包，输出**两份修改计划文档**（PRD 修改计划 + 原型修改计划）。本技能是"修改闭环"中的**计划环节**：只梳理怎么改、不改任何文件；真实修改由产品经理确认计划后另行执行（届时可调用其他 skill 提升修改效果）。

## 输入契约

平台评论导出 zip（`GET /api/projects/{id}/comments/export`，仅项目创建者可导出）：

```
{project_id}-comments-{yyyymmdd}-{HHmm}/
├── manifest.json     # {exported_at, project{id,name}, scope, total, comments[{comment_id,status,has_shot}]}
├── comments/         # 每条评论一个 JSON
└── shots/            # 评论整页截图 PNG（仅被导出评论引用且存在的）
```

评论 JSON 关键字段（完整契约见《产品方案-V1.md》§3.3；priority/scope 已移除）：

| 字段组 | 字段 | 用途 |
|--------|------|------|
| 元信息 | comment_id / author / status / content / created_at | status 五态；**仅「已确认待修改」进入修改计划** |
| 宿主判断 | target_type | `doc_block`=PRD 文档评论；`dom`/`page`=原型评论 |
| 原型定位 | prototype_page / anchor_id / nearest_anchor_id / css_path / outer_html / text_excerpt | 定位原型页面与元素 |
| PRD 定位 | doc_anchor_id / doc_excerpt / doc_file / doc_block_fingerprint | 定位 PRD 段落（锚点优先，指纹兜底） |
| 视觉上下文 | screenshot / highlight_rect | 截图在导出包 shots/ 内，红框圈出目标区域 |

## 主流程

### 第 1 步：解压与概览

用本技能自带脚本解压导出包并输出摘要（零依赖；安全解压，拒绝路径穿越/软链/炸弹）：

```bash
python <本技能目录>/unpack_comments.py <导出包.zip>          # 文本摘要
python <本技能目录>/unpack_comments.py <导出包.zip> --json   # 机器可读（推荐，供逐条处理）
```

脚本自动完成：安全解压 → 读 manifest → 逐条读 comments/*.json → 按状态/宿主分组统计 → 列出全部「已确认待修改」评论（含定位提示、有无截图、有无 PRD 关联）。

### 第 2 步：逐条梳理「已确认待修改」评论

对每条已确认待修改评论，按宿主分两路处理。**一次只处理一条，处理完再下一条。**

**路径 A：评论宿主是 PRD 文档（target_type=doc_block）**

1. 用 `doc_anchor_id` 在 PRD 中搜索 `<!-- pa: 该ID -->` 找到对应段落；锚点缺失时用 `doc_excerpt`（段落原文摘录）做文本搜索兜底；仍找不到则标记"定位失败，待人工确认"并向产品经理提问。
2. 通读该段落及上下文，结合评论 content 梳理 PRD 如何修改（改规则描述/改验收标准/增删条目等）。
3. **联动判断**：判断该 PRD 修改是否涉及原型变更（如"密码至少 8 位"改"至少 10 位"→ 原型表单校验文案与逻辑要跟着改）。涉及则在原型修改计划中列出对应页面/元素及改法，通过锚点 ID 或 PRD 描述定位原型侧位置。

**路径 B：评论宿主是原型（target_type=dom/page）**

1. 用 `prototype_page` + `anchor_id`/`nearest_anchor_id` 定位页面与元素；无锚点时用 `css_path`、`text_excerpt`、`outer_html` 在该页面源码中搜索定位。查看 `screenshot`（导出包 shots/ 内）理解视觉上下文。仍找不到则标记"定位失败"并向产品经理提问。
2. 通读该元素及所在页面代码，结合评论 content 梳理原型如何修改。
3. **联动判断**：
   - 若评论带 `doc_anchor_id`/`doc_excerpt`（命中 PRD 锚点），检查 PRD 对应段落是否需要同步修改；
   - 若评论无 PRD 关联（doc_note="无 PRD 锚点关联"），按平台契约这是信号：**该处原型行为在 PRD 中缺描述**，需在 PRD 修改计划中补一条"为该功能补充 PRD 描述"。

**提问纪律**：梳理过程中遇到以下情况，**停下来向产品经理提问确认后再继续**，不要自行拍板：
- 评论意图模糊，可作多种理解（改文案 vs 改交互 vs 改规则）
- 修改方案有多种合理选择且影响范围不同
- 联动判断拿不准（说不清是否涉及另一侧变更）
- 定位失败（锚点/摘录/搜索都找不到目标段落或元素）

### 第 3 步：产出两份修改计划

汇总全部已确认待修改评论的梳理结果，分别输出：

- `PRD修改计划-{项目名}-{日期}.md`
- `原型修改计划-{项目名}-{日期}.md`

每份计划的结构：

```markdown
# {PRD/原型}修改计划 · {项目名}（{导出时间}）

> 来源：评论导出包 {zip 文件名}，scope={scope}，已确认待修改 {N} 条。
> 本计划仅为梳理结果，待产品经理确认后另行执行修改。
```

**排序建议**：按 PRD 章节 / 原型页面组织修改项，便于按文件顺序执行；每项都标注来源评论 ID，保证可回溯。

### 第 4 步：交付与确认

1. 把两份计划文件保存到约定位置（默认：导出包同目录）。
2. 向产品经理汇报：修改项数量、跨侧联动项数量、待确认事项清单。
3. 产品经理逐项确认/调整后，本技能职责结束；正式执行修改时由产品经理另行发起（可配合 prd-html-anchor 技能保证锚点契约、或调用其他修改辅助 skill）。

## 边界与纪律

- **只梳理，不修改**：全程不改动 PRD、原型、评论文件中的任何内容。
- **只处理「已确认待修改」**：其他状态（待确认/已修改/忽略/延后再改）不进入计划，但在汇报时说明数量。
- **每条可回溯**：所有修改项必须标注来源 comment_id。
- **不确定必须问**：宁可中断提问，不猜测产品经理意图。
- **联动变更双侧对账**：PRD 改了原型要不要改、原型改了 PRD 要不要改，每个修改项都要显式给出结论（含"不涉及另一侧"这一结论本身）。

## 配套脚本

`unpack_comments.py`（与本 SKILL.md 同目录，零依赖，Python 3.10+）：

- 输入：导出 zip 或已解压目录；`-o` 指定解压目录；`--json` 机器可读输出；`--quiet` 单行汇总
- 退出码：0=成功且有已确认待修改；1=无已确认待修改；2=解压/结构错误
- 安全：拒绝路径穿越/软链，总量 ≤300MB、条目 ≤5000（与平台上传安全口径一致）
